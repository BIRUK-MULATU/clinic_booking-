2. What was not tested

  • Concurrency. Two patients racing to book the same slot at the same instant is not tested; C1 (existsBySlotAndStatusIn) is correct for sequential requests but has no explicit test under concurrent load, and no database-level uniqueness constraint backs it up. This is the single largest functional gap and is carried as residual risk below.
  • Real SMS delivery. By design (CLAUDE.md), NotificationService has only a logging implementation; there is no real gateway to test against.
  • Non-functional testing — load, performance under many concurrent users, accessibility, and security penetration testing are all out of scope per the test plan (§1.2).
  • A handful of defensive/unreachable branches — e.g. a catch-all path in GlobalExceptionHandler and a couple of simple getters never called by any test — are the reason whole-application instruction/line coverage (~90%/~89%) sits below the 100% branch figure on core; none of this uncovered code sits inside the three graded business rules.

5. Release recommendation

Recommendation: ready to submit, with the concurrency gap disclosed as a known limitation rather than fixed.

All exit criteria in §3 are met, the coverage gate is exceeded (100% vs. an 80% target) on the graded package, all three defects found during development are closed and verified, and the regression-detection requirement has real, reproducible evidence (two CI run links, a failing one and a passing one) rather than a description of what would happen. For a course project whose explicit grading criterion is the testing effort rather than the application's production-readiness, this is a defensible stopping point.

The one open item — concurrent double-booking — is a real, named risk rather than an unknown one, which is itself the point of a test summary report: it exists precisely to say plainly what was not covered, not just to report a clean scorecard. If this were a real clinic system rather than a course project, that gap would block release; here, it is disclosed and left as a direction for further work rather than fixed under time pressure this close to the deadline, since fixing it correctly would mean adding a database constraint and its own test coverage rather than a quick patch.

6. Foundations reflection — error, fault, failure; verification vs. validation

The defect: DEF-003, the flaky Selenium page-object bug found while verifying the Jenkins pipeline (full write-up in the defect log). BookingJourneyIT passed reliably in GitHub Actions but threw NoSuchElementException the first time it ran inside the Jenkins Docker container.

  • Error — the human mistake behind the defect was a mental model slip while writing the page objects: assuming that once Selenium's click() call returns after triggering a redirect, the destination page has already finished rendering. That assumption is not guaranteed by the WebDriver spec, which only promises that a triggered navigation has started, not that it has completed.
  • Fault — the resulting defect in the code: every page object called driver.findElement(...) directly, with no wait, immediately after a click that caused a navigation. The fault sat dormant in every page object from Phase 7 onward.
  • Failure — the observable, external symptom: BookingJourneyIT threw NoSuchElementException looking for #confirmation-status, but only under the tighter CPU budget of the Docker container — the same fault produced no failure at all on the faster GitHub-hosted runner, which is exactly why a fault can sit latent for a long time before a particular environment turns it into a visible failure.

Verification or validation? This was caught by verification, not validation. Verification asks "are we building the product right" — checking the system against its own specification and internal correctness, which is exactly what an automated system test running inside a CI pipeline does: it re-runs a known, specified user journey and checks the code behaves correctly, with no real user or stakeholder involved. Validation — checking with an actual user or against real-world use ("are we building the right product") — never entered into finding this defect at all; no person ever clicked through the failing journey. That the defect only appeared under one specific execution environment (constrained CPU) is itself a small lesson in why verification has to include more than one environment: the GitHub Actions run alone would have verified the same specification and still missed this fault entirely.
